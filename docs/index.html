01Question

Using only the lap times a team has seen so far, can a model tell when a Formula 1 driver is about to pit, within ±2 laps of the actual stop, better than a tyre-age rule and a logistic-regression classifier?

Teams pit mostly because tyres wear out, and worn tyres make lap times slower. But tyre condition is not public. So we treat it as a hidden state and infer it from lap times with a hidden Markov model (HMM) that we wrote from scratch.

After every lap, each model decides whether to raise an alarm ("this driver will pit now"). It may only use laps that have already happened. An alarm counts as correct if a real pit stop happens within ±2 laps of it.

What we claim, and what we don't

  • Pit stops are only a proxy for tyre wear. Teams also pit for strategy (undercuts, safety cars, traffic), so some stops cannot be predicted from lap times at all.
  • This is prediction, not causation.
  • A useful answer is an honest comparison with simple baselines on a season the models never saw, plus a look at where they fail. A modest or negative result is still an answer.

Two terms

A stint is the run of laps between two pit stops (or between the last stop and the finish). An alarm is a model's call to pit on a given lap.

We use the Kaggle "Formula 1 World Championship" dataset (Rohan Rao), built from the Ergast motor-racing database: races.csv, lap_times.csv, pit_stops.csv and results.csv.

One row = one lap by one driver in one race. Scope: all 196 races from 2011 (start of the Pirelli era) to 2020.

Of the 11,242 stints, 7,318 end in a pit stop. The other ~35% end at the chequered flag, so a model that raises an alarm late in every stint will be wrong about a third of the time by design.

Why not FastF1? Our original plan used the FastF1 library, which has compounds and track status. On 15 October 2026, F1 moved its live-timing archive behind a paid F1 TV subscription, so we switched to Ergast/Kaggle and lost those columns.

Seasons, licence and why the study stops at 2020

The Kaggle CSVs cover 1950–2024. We use 2011–2020 only; 2021–2024 were never loaded by the pipeline, so they remain an untouched second test set for future work. The dataset is released under CC0: Public Domain, which is why the four CSVs can be committed to this public repository.

The 2011–2020 window and the train / validation / test split were fixed in our proposal, before any model was run. We kept them when we moved from FastF1 to Kaggle so that the 2020 test season stayed untouched.

2019 picks the number of HMM states (2, 3, 4) and every alarm threshold. Final models are refit on 2011–2019 with the 2019 settings, then run once on 2020.

Cleaning rules and leakage checks
  • Drop the first lap of each race (standing start, not representative).
  • Drop pit-in and pit-out laps (time lost in the pit lane, not on tyres).
  • Drop laps slower than 1.35× the driver's median lap in that race (safety cars, incidents, traffic).
  • Stints are inferred from pit-stop laps, since Ergast has no stint column.
  • The feature scaler is fit on training seasons only.
  • Nothing is chosen on 2020. The pipeline refuses to run the 2020 test a second time or to retune after it.
  • Splitting by season (not by random laps) stops laps from the same race leaking between train and test.

Known issue: the median in the 1.35× rule is taken over the whole race, so it uses a little information from later laps. It only decides which laps are dropped, not any feature value, but a fully causal version would use the median so far.

03Method

An HMM written from scratch, against two simple baselines, plus a version of the HMM with tyre age removed to see what the lap times alone can do.

Main method

HMM

Gaussian HMM written from scratch (scaled forward–backward, Viterbi, Baum–Welch). Trained without pit labels. After each lap, forward filtering gives P(worn | laps so far). One alarm per stint when this passes a threshold (0.3–0.9, picked on 2019).

Ablation

HMM without tyre age

Same HMM, but tyre age removed from its inputs. If it does as well as the full HMM, the lap times carry the signal; if it collapses, the HMM was mostly counting laps.

Baseline

Tyre-age rule

One alarm per stint, when tyre age passes a threshold. Threshold picked on 2019 from 0.60–0.95 (24–38 laps). Asks: is counting laps enough?

Baseline

Logistic regression

Per-lap classifier on the three features, labelled "pit within the next 3 laps", with class weights for the rare positives. An alarm is raised at the start of each run of positive laps, so it can raise several per stint.

How the HMM is set up

Two states, chosen on 2019. Tyres never recover, so there is no arrow back.

  • Left-to-right transitions: the model can stay fresh, move to worn, or stay worn, but never go back.
  • Starts fresh: π = [1, 0]. Each stint is a new sequence.
  • Gaussian emissions: each state has its own mean and spread for the lap features.
  • Filtering, not Viterbi: Viterbi looks at the whole stint, including the future. Forward filtering uses only laps up to now, which is what a pit wall actually has.
  • Two states, chosen on 2019: we tried 2, 3 and 4 states. The best 2019 F1 was 0.091 with 2 states, against 0.089 with 4 and 0.058 with 3. Both the full HMM and the ablation chose 2 states.
  • Why an HMM? There are no labels for tyre condition, laps within a stint depend on each other, and the learned states and transitions can be read and checked.

Two checks from the proposal were not done: a Gaussian mixture model (an HMM with no time component) and a comparison of our HMM against hmmlearn. See Limitations. The third, alarms before vs after the pit, is in Errors.

How we score the models

One-to-one matching

Within each driver-race, each alarm is matched to at most one real pit stop. Within ±2 laps is a hit; extra alarms are false positives; unmatched pits are misses.

Pooled F1, not accuracy

Precision, recall and F1 from TP/FP/FN summed over all driver-races. Pits are about 1 lap in 28, so "never pit" would score over 96% accuracy.

2019 tunes, 2020 tests

All choices use 2019; 2020 is used once. Results are also reported at ±1 and ±3 laps, and alarm timing shows whether models are early or late.

Interactive: the precision–recall trade-off on 2019

Each threshold was tried on the 2019 validation season. A lower threshold raises alarms earlier and more often (higher recall, more false alarms); a higher one is pickier. The ringed point is the setting chosen by best F1 and used on 2020.

06Errors: when and why models miss

Most false alarms come in the final stint, where worn tyres are never changed. Most identifiable misses are stops that have nothing to do with gradual wear.

Are alarms early or late?

For every alarm paired with a pit in the same driver-race: alarm lap − pit lap. Negative = early (useful to a team), positive = after the stop had already happened.

Caveat: the timing file pairs each alarm with the nearest unused pit in that driver-race, with no distance limit and not restricted to the same stint. So far-away pairs (the outer bars) are often an alarm in one stint paired with a pit from another, not a real near-miss.

In the ±2 matching used for the results, all 46 of the HMM's correct alarms came 1–2 laps before the stop and none on or after it. The timing chart pairs alarms differently (hence 42), but it also shows no late hits. So the alarm-after-the-pit problem from the tyre-age bug (see Limitations) is gone.

07Conclusion

No.

Using lap times alone, none of the models predicts the pit lap well, and the HMM does no better than counting laps: F1 = 0.106 at ±2 against 0.107 for the tyre-age rule and 0.085 for logistic regression.

Why

Many stops are not caused by gradual wear: whole-field stops under interruptions, early stops after short stints, and strategic calls. Meanwhile the most worn tyres of the race, in the final stint, are never changed. Without compounds and track status, a model sees the same lap-time pattern in all of these cases.

What would help

Compound and safety-car data, and predicting a window of laps instead of an exact lap: the HMM is clearly better at ±3.

What we take away

An unsupervised HMM gives an interpretable, causal estimate of tyre state, but the pit lap depends on much more than tyre state, and a symmetric tolerance window can hide models that only react after the fact.

08Limitations and what went wrong

A bug made our first test results invalid

On 28 October 2026 we found that a pandas merge reset the row index, so tyre age was read from the wrong laps for about 96% of rows. At the start of each new stint the feature still carried the old stint's high value, so models raised alarms 1–2 laps after a pit. The symmetric ±2 window counted these as correct. About three quarters of logistic regression's correct alarms came from this.

We fixed it by counting kept laps within each stint, then re-ran tuning, training and the 2020 test from scratch. The first 2020 test was invalid. No setting was chosen by looking at 2020 results, before or after the fix.

Lesson: a symmetric tolerance window rewards alarms that come after the event. That is why we also report the timing of alarms (see Errors).

Other limitations

No tyre compounds. Softs and hards wear at very different rates; one model and one "40-lap" scale must cover both.
No safety-car or weather flags. Many stops happen because a safety car makes them cheap, not because tyres are worn. We can't remove those laps or races cleanly.
Pit laps are a noisy label. Strategy (undercuts, covering a rival, traffic) moves stops by several laps.
One test season. 2020 was unusual (COVID calendar, repeat circuits, 17 races), so results may not carry over to other seasons.
Unequal chances. Logistic regression can raise several alarms per stint; the others raise at most one.
Cleaning median uses the whole race (see Data → cleaning rules).
Timing pairs are not limited to the same stint (see the caveat under Errors).
Two proposal checks not done: no Gaussian mixture model comparison and no check of our HMM against hmmlearn.
Unit tests are out of date. tests/test_pipeline.py imports a helper that was later removed from the pipeline, so the test file does not currently run.
Tyre-age threshold at the edge of the grid. 2019 picked 0.60, the lowest value tried, so a lower threshold might have done better.

09Reproduce

Python 3.12.0, pipeline code at commit 7f934e9 (the tyre-age fix), 2020 test run on 28 October 2026.

Run it yourself 
git clone https://github.com/AceAryan/f1-pitstop-hmm.git
cd f1-pitstop-hmm
pip install -r requirements.txt

python main.py --preprocess                    # clean laps, build features, split by season
python main.py --tune                          # fit on 2011–2018, choose settings on 2019
python main.py --train --test_year 2020        # refit on 2011–2019 with the 2019 settings
python main.py --evaluate --test_year 2020     # one-time test on 2020

Data: the four Kaggle CSVs are already in data/kaggle/. To refresh them, download the Kaggle dataset and copy races.csv, lap_times.csv, pit_stops.csv and results.csv into data/kaggle/.

Outputs: results/evaluation_pooled_summary.csv, results/prediction_timing_deltas.csv and two JSON files in results/site-data/. The results/ folder is not committed; the copies this site reads are in docs/data/.

Rebuild this website 
bash docs/tools/update_site_data.sh     # copy results into docs/data and drop the placeholder flag
python -m http.server -d docs 8000      # preview at http://localhost:8000

The site is plain HTML, CSS and JavaScript in docs/ with no build step. Open it through a web server (as above, or GitHub Pages), not by double-clicking the file, because browsers block loading data files from disk.
